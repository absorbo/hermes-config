# rsync Protocols (Vault ↔ Hermes-Config)

> **Live state lives in `~/.hermes/`. The vault is a read-only mirror for user visibility and SOUL.md commit-gate enforcement. Direction is ONE-WAY: hermes → vault. NEVER the reverse for any runtime-written directory.**

## Repos

| Role | Path | Editable? | Live state owner? |
|---|---|---|---|
| PRIMARY (authoritative — runtime) | `~/.hermes/` | YES (the scheduler writes here) | YES — the cron ticker, gateway, kanban all write here |
| SECONDARY (mirror — user visibility) | `~/Library/Mobile Documents/iCloud~md~obsidian/Documents/Obsidian/05 - AI/99 - Hermes/` | NO — regenerated by rsync | NO — copy only |

## Direction: hermes → vault (the ONLY direction that should ever run for live state)

`~/.hermes/cron/jobs.json`, `gateway_state.json`, `processes.json`, `auth.json`, SKILL.md files, scripts/, etc. are live state the runtime OR the user edits in `~/.hermes/`. The vault mirror exists for two reasons: (1) the SOUL.md commit gate requires the mirror to be in sync before pushing hermes-config, (2) the user wants their operational state visible in Obsidian.

```bash
# The canonical sync. Exclude runtime-written blobs and secrets-bearing files
# that the vault mirror does not need.
rsync -av \
  --exclude='state.db*' \
  --exclude='state-snapshots/' \
  --exclude='sessions/' \
  --exclude='logs/' \
  --exclude='hermes-agent/' \
  --exclude='venv/' \
  --exclude='.env' \
  --exclude='.env.pre-revert.*' \
  --exclude='cron/output/' \
  ~/.hermes/ \
  "<vault>/05 - AI/99 - Hermes/"
```

**DO NOT use `--delete` on this rsync.** The vault mirror is incomplete by design (the exclude list skips files the vault does not need). `--delete` would destroy any user-written file in the mirror that is not in the source. The vault pre-commit hook (`hermes-config-management` skill) catches the 3 critical files (`config.yaml`, `SOUL.md`, `prefill.txt`); broader drift is the agent's responsibility.

## Direction: vault → hermes (DO NOT do this for live state)

There is no legitimate reason to rsync the vault mirror back into `~/.hermes/` for any runtime-written directory. The cron sandbox resolves scripts through wrappers at `~/.hermes/scripts/` that `exec` the vault source of truth (see `references/portable-cron-script-pattern.md` in `cron-pipeline`) — the source IS the vault, no copy back is needed.

If you find yourself about to run `rsync ... <vault>/... ~/.hermes/...`, STOP. This is the rsync direction that caused the 2026-06-06 incident where live `cron/output/` log files were deleted by `--delete`, plus a stale `jobs.json` was copied over the live one (see Verified case study below).

## Hard rule: ad-hoc cross-repo rsync is forbidden

Do NOT run `rsync` between the vault and `~/.hermes/` from the agent loop. Ever. The only sanctioned flows are:

1. **hermes → vault mirror**, run by the pre-commit hook (or the agent running the EXACT pre-commit command verbatim, never with improvisation). Excludes below.
2. **vault source → hermes wrapper**, by editing the wrapper in `~/.hermes/scripts/*.sh` to `exec` the vault path. No rsync needed — the exec is a one-line path translation.

If you think you need to rsync between the two repos, you don't. Either:
- It's a one-file copy → use `cp` with absolute paths, after showing the user the two paths.
- It's a state propagation → it's already handled by the wrapper pattern.
- It's a "let's confirm they're in sync" → run a `diff` or `cmp`, not an rsync. The diff output is the verification; do not then "fix" the drift by syncing without explicit user direction.

**2026-06-06 case study:** I ran `rsync -av --delete vault/cron/ hermes/cron/` to "confirm state". Wrong direction. `--delete` then destroyed 3 live log files and overwrote live `jobs.json` with the older mirror. Cost: a `git checkout HEAD -- cron/jobs.json` to recover, plus 3 permanently lost log files. The "fix" introduced the damage. Don't repeat.

## Pitfalls (for the one allowed flow: hermes → vault, pre-commit only)

| # | Pitfall | Consequence |
|---|---------|-------------|
| 1 | `rsync --delete` with wrong direction | Source becomes dest, dest becomes source. Live state gets overwritten by stale mirror. Verified 2026-06-06. |
| 2 | `rsync --include cron/output/` | 3 log files destroyed 2026-06-06. Exclude the entire `output/` subdir — those are runtime logs the scheduler writes. |
| 3 | Including `state.db*` in vault mirror | 43MB+ binary blob; useless in vault. Always exclude. |
| 4 | rsyncing `~/.hermes/.env` to vault | May contain interactive prompts / auth material; exclude. |
| 5 | rsyncing `sessions/` or `logs/` to vault | Massive, useless, bloats vault. Exclude. |
| 6 | Improvising the exclude list on the fly | Use the canonical exclude list below. No ad-hoc additions. |

## Canonical exclude list (the only one allowed)

```text
state.db
state.db-shm
state.db-wal
state-snapshots/
sessions/
logs/
hermes-agent/
venv/
.env
.env.pre-revert.*
```

No `cron/output/`, no `*.lock`, no exceptions. If the pre-commit hook is too restrictive, edit the hook — do not pass extra flags to the rsync call.

## Verified case study (2026-06-06)

While auditing the cron pipeline, I did `rsync -av --delete` from the vault mirror of `cron/` to `~/.hermes/cron/`. The vault's `cron/output/` was stale; the hermes had live log files from 2026-06-06 11:54 / 18:50 / 18:52. `--delete` destroyed them. Also overwrote `~/.hermes/cron/jobs.json` with the older vault copy, which had wrong script paths (`<vault>/scripts/cron_output_rotate.sh` instead of the `~/.hermes/scripts/` wrapper). Cron sandbox would have rejected the vault-path script on next tick. Restored via `git checkout HEAD -- cron/jobs.json` (correct wrapper paths from the committed version). Log files are permanently gone.

**Lesson:** rsync direction + `--delete` is the most dangerous combo in this codebase. When in doubt: do NOT use `--delete` for any subdirectory that the cron scheduler writes to (`output/`, `logs/`, `state.db*`).
